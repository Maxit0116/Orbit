# AI Task Workspace 产品 PRD

**文档版本**：0.1  
**产品代号**：Orbit  
**目标平台**：微信小程序  
**文档目的**：指导参赛 MVP 的产品设计、交互实现、技术拆解和比赛演示  
**范围声明**：本文只定义产品，不包含业务代码。产品面向所有需要组合微信小程序完成的现实任务；旅行和异地过年只是验证模板，不是产品边界。微信开放能力的验证结论以 `docs/DEVELOPMENT_PLAN.md` 的技术核验矩阵为准。

## 1. Product Vision

> 不要帮用户寻找小程序，而是为用户正在完成的现实目标创建一个 Workspace。

Orbit 的最小产品单位不是小程序、搜索结果或一段 AI 答案，而是一个围绕现实任务持续存在的 **Task Workspace**。用户只需描述目标，Orbit 负责把目标拆成可执行任务，为任务匹配精选工具，记录用户确认的结果，持续检查进度、预算、时间和多人分工。

产品闭环：

```text
Intent
  -> Task Decomposition
  -> Capability Matching
  -> Task Workspace
  -> User-confirmed Facts
  -> Cross-task Guidance
  -> Collaboration
```

### 1.1 参赛命题

本产品服务于 2026 微信小程序开发大赛的“与 AI 共生”方向。参赛价值不是“把大模型接进小程序”，而是展示 AI 如何重新组织微信小程序的使用方式：

- 微信搜索的单位是小程序；
- AI 推荐产品的单位是答案和链接；
- Orbit 的单位是任务空间，以及空间内可持续更新的 Context。

### 1.2 非目标

以下内容不属于 MVP 的承诺：

- 搜索或抓取全量微信小程序生态；
- 读取任意第三方小程序的页面、订单、登录态或数据库；
- 自动代替用户下单、支付、预约、改签或提交敏感信息；
- 做通用聊天机器人、单一垂直服务平台或全域比价平台；
- 用群关系链自动发现和管理所有好友；
- 用“AI 生成的模拟数据”冒充第三方小程序真实返回结果。

### 1.3 MVP 要验证的核心假设

1. **Intent 假设**：用户可以用一句自然语言描述不同类型的现实任务，AI 能生成一个可编辑、可执行的任务结构。
2. **Capability 假设**：不同微信小程序可以作为任务能力被组织到同一个 Workspace，而不是只能作为并列链接。
3. **Context 假设**：当多个服务结果被用户确认并汇入同一 Workspace 后，系统能发现单个小程序无法发现的时间、预算、依赖或协作问题。

## 2. Problem Statement

用户完成一次现实任务时，通常需要在多个小程序之间来回切换。每个小程序只知道自己的局部交易或服务上下文，用户必须自己记住：

- 目标是什么、哪些步骤已经完成；
- 不同工具之间的时间、地点、预算是否冲突；
- 谁负责哪一步；
- 之前在另一个小程序里选了什么；
- 下一步应该打开哪个工具。

现有体验把任务拆散成：

```text
用户需求 -> AI 或搜索结果 -> 多个孤立小程序
```

Orbit 要把它变成：

```text
用户目标 -> AI 拆解 -> Task Workspace -> 多个任务工具 -> 统一事实与建议
```

## 3. Target Users

### 3.1 MVP 主用户：复杂现实任务的组织者

- 年龄：18–40 岁；
- 高频使用微信，习惯用小程序完成生活服务；
- 需要为自己、家庭或 2–6 人团队安排一件有时间、预算、地点或分工约束的事情；
- 愿意接受 AI 的初步方案，但希望自己确认关键选择；
- 典型身份：家庭事务负责人、搬家组织者、聚会发起人、异地团聚组织者、旅行计划者。

### 3.2 次级用户：被邀请的协作者

- 不一定了解 Orbit；
- 通过微信分享卡片进入；
- 主要查看任务、认领任务、提交结果和确认决策；
- 不应被迫阅读复杂的 AI 对话。

### 3.3 代表性任务类型

- 跨城/异地家庭团聚；
- 搬家；
- 朋友聚会；
- 家庭事务；
- 旅行；
- 临时团队项目负责人。

## 4. User Pain Points

| 痛点 | 现有替代方案 | Orbit 的解决方式 |
| --- | --- | --- |
| 需求复杂，搜索词难写 | 多次搜索、问朋友 | Intent 结构化解析，先显示假设并让用户确认 |
| 小程序彼此孤立 | 手工记在聊天、备忘录 | 任务卡绑定工具和用户确认事实 |
| 信息会互相冲突 | 靠人脑检查 | 规则引擎检查时间、预算、依赖 |
| 多人分工混乱 | 群聊刷屏、重复询问 | Task Owner、状态、评论和 Workspace Summary |
| AI 推荐不可信 | 直接相信答案或逐个验证 | 精选知识库、来源标记、可解释匹配和人工确认 |
| 操作结果无法回到 AI | 复制粘贴或重新描述 | 结构化“加入 Workspace”表单，保存来源和时间 |

## 5. Competitive Analysis

### 5.1 对比

| 维度 | 微信搜索 | 元宝类 AI 推荐 | Orbit |
| --- | --- | --- | --- |
| 核心单位 | 小程序 | AI 答案 | Task Workspace |
| 输入 | 关键词 | 自然语言 | 自然语言或语音 |
| 产出 | 搜索结果 | 文本、链接、推荐 | 可编辑任务树与工作空间 |
| 上下文 | 当前查询 | 当前会话 | 目标、事实、状态、成员、决策 |
| 跨工具关系 | 无 | 主要是并列链接 | 任务依赖、预算、时间线和冲突 |
| 协作 | 需要另开群聊 | 非核心 | 围绕任务认领、状态和决策 |
| 结果回流 | 无 | 通常由用户重新描述 | 用户确认后写入 Workspace Context |
| 主要风险 | 找不到合适入口 | 推荐与事实幻觉 | 第三方数据接入边界 |

### 5.2 竞争差异的证伪条件

如果用户在使用 Orbit 时仍然需要：

1. 先去微信搜索；
2. 逐个打开推荐小程序；
3. 自己在聊天或备忘录里记录结果；
4. 自己检查时间和预算；

那么 Orbit 只是更漂亮的导航页，不构成独立价值。MVP 必须至少让评委看到一次“两个任务结果汇合后产生新判断”的体验。

## 6. Product Positioning

### 一句话定位

**Orbit 是一个以任务为中心的 AI 小程序工作空间，把分散在微信生态里的服务组织成可执行、可协作、可持续理解的目标空间。**

### 核心价值主张

1. **从目标开始**：用户不需要知道应该搜索什么小程序。
2. **任务可执行**：AI 输出任务和下一步，而不是只给答案。
3. **工具归属于任务**：小程序是完成子任务的工具，不是独立收藏。
4. **事实可回溯**：用户确认的预算、时间、地点和选择都有来源。
5. **跨任务有增量智能**：AI 用多个任务的事实发现冲突、缺口和下一步。
6. **微信原生协作**：通过分享和实时同步让共同目标进入熟悉的微信关系链。

## 7. Representative Validation Template

### 7.1 产品边界

Orbit 的目标不是“旅行 Workspace”，而是“任何需要多个微信小程序共同完成的现实任务 Workspace”。

可覆盖的任务包括：

- 异地过年：交通、礼物、年货、餐饮、住宿、家庭分工、预算；
- 搬家：租房、搬家公司、家具、快递、水电、地址变更、预算；
- 聚会：餐厅、交通、活动预约、AA 记账、成员分工；
- 家庭事务：医院、预约、交通、缴费、材料、提醒；
- 旅行：交通、酒店、门票、行程和预算。

这些场景共享同一套产品内核：目标、约束、任务、工具、事实、状态、成员和下一步建议。

### 7.2 比赛验证模板：异地过年

为了避免 MVP 变成多个半成品，比赛只选一个代表性模板验证通用框架：

> 春节我和家人分散在不同城市，想一起回老家过年。请帮我安排交通、住宿、年货和家庭分工，预算 6000 元。

选择这个模板不是把产品限定为节日出行，而是因为它能同时验证：

- 多种小程序能力：出行、住宿、购物、本地生活、记账；
- 多约束：城市、日期、人数、预算、到达时间；
- 强协作：家庭成员分别负责交通、年货和餐饮；
- 跨任务关系：到达时间影响聚餐，采购时间影响收货；
- 微信生态优势：分享、多人加入、实时同步和订阅提醒。

旅行仍然保留为另一种任务模板和对比示例，不再作为产品定位或唯一 Killer Scenario。

## 8. Core User Journey

### 8.1 主流程

1. 用户进入首页，输入或录入语音 Intent。
2. AI 解析目标、参与者、地点、时间、预算、偏好、约束和缺失信息。
3. 用户在“确认任务计划”页修改字段和任务。
4. 系统创建 Workspace，展示任务树、进度、预算和时间线。
5. 用户打开与当前任务匹配的一个或多个微信小程序工具。
6. 用户完成外部操作后，选择“加入 Workspace”，填写或确认结构化结果。
7. Workspace 更新任务状态、预算、时间、地点和其他任务事实。
8. 规则引擎检测到时间、预算、依赖或责任人冲突。
9. AI 生成有证据引用的建议，用户接受、忽略或修改。
10. 用户分享 Workspace，第二个成员加入并看到实时状态。

### 8.2 首次解析的可编辑结果

解析页必须优先展示“AI 的理解”，而不是直接进入不可逆的自动化：

- 目标：异地家人春节团聚；
- 成员：父母、用户、兄弟姐妹；
- 出发城市：多个；
- 目的地：老家；
- 时间：春节假期 / 具体日期未知；
- 任务范围：交通、住宿、年货、聚餐、家庭分工；
- 总预算：6000 元；
- 偏好：待补充；
- AI 假设：预算是否包含所有成员交通和年货；
- 待确认问题：具体城市、日期、成员人数和是否需要住宿。

## 10. Feature Architecture

### 10.1 MVP 功能

| 模块 | MVP 功能 | 明确不做 |
| --- | --- | --- |
| Intent | 文本输入、结构化解析、确认和修改 | 长期记忆、开放域自动执行 |
| Task | 任务树、状态、依赖、负责人、手动增删改 | 任意复杂 DAG 编辑器 |
| Discovery | 精选知识库、规则匹配、推荐理由、跳转 | 全网搜索、实时全生态索引 |
| Workspace | 概览、任务、预算、时间线、事实、活动记录 | 文档协同、富文本知识库 |
| Context | 结构化事实、事件、摘要、冲突检测 | 任意第三方数据自动读取 |
| Tool handoff | 跳转或展示可用入口、手动提交结果 | 自动获取订单或自动下单 |
| Collaboration | 分享卡片、Owner/Member、认领、完成、实时更新 | 好友列表、群成员管理 |
| AI Agent | 任务拆解、摘要、下一步、冲突建议 | 自动做支付/预约等高风险动作 |
| Notification | 页面内提醒，关键消息的用户主动订阅 | 无授权的主动推送 |

### 10.2 V1 功能

- 任务模板：搬家、聚会、旅行、家庭事务；
- 异地过年模板的更多城市和精选服务能力；
- 图片/截图解析为候选事实，用户确认后入库；
- 评论和任务内讨论；
- 可配置提醒和更多订阅消息模板；
- 合作方提供的结构化回传适配器；
- 多方案版本比较。

### 10.3 Future

- 合作小程序之间的标准化 Capability Contract；
- 经过授权的跨产品数据回传；
- 多人投票、费用结算和更复杂的团队权限；
- 面向企业或社群的 Workspace 模板；
- 基于已完成任务的个性化建议；
- 跨 Workspace 的用户偏好，但必须单独设计隐私和删除机制。

## 11. Workspace Architecture

Workspace 不是收藏夹，而是一个可持续更新的现实任务 Context。

### 11.1 Overview

- Goal：用户最终想达成的目标；
- Status：未开始、进行中、存在风险、已完成；
- Progress：已完成任务 / 总任务；
- Next Action：当前最有价值的下一步；
- AI Summary：基于已确认事实生成，必须显示更新时间；
- Risk Banner：时间、预算、缺少负责人或缺少必要输入。

### 11.2 Task

每个 Task 至少包含：

- 名称和说明；
- 状态：`todo / in_progress / blocked / done / skipped`；
- 优先级；
- Owner；
- 依赖任务；
- 时间窗口；
- 预算范围和实际金额；
- 匹配的 Capability；
- 用户确认结果；
- 活动记录；
- AI 建议和建议依据。

### 11.3 Tool

Tool 卡片必须让用户感受到“这是完成当前任务的工具”：

- 显示所属 Task；
- 显示“为什么推荐”；
- 显示所需输入；
- 显示预期输出；
- 显示跳转方式和可用性；
- 显示数据来源和最后核验时间；
- 跳转前告知“完成后需回到 Orbit 确认结果”；
- 若不可跳转，提供搜索词、复制入口或手动记录入口。

### 11.4 Decisions

关键选择单独记录，例如：

```text
决定：选择 12 月 28 日上午高铁回老家
由：用户本人
时间：2026-08-30 20:15
依据：¥520 / 人，预计 13:00 到达
影响：可以赶上当晚家庭聚餐，但年货需提前送达
```

## 12. AI Workspace Agent

### 12.1 Agent 职责

Agent 负责四类工作：

1. **Understand**：把自然语言变成结构化 Intent；
2. **Plan**：生成任务树、输入需求和任务依赖；
3. **Observe**：从 Workspace 的事件和事实中观察状态变化；
4. **Guide**：给出下一步、冲突、缺口和协作建议。

Agent 不负责：

- 代替用户做支付和不可逆操作；
- 声称读取了第三方小程序页面；
- 在没有来源的情况下填充价格、班次和余票；
- 直接覆盖用户确认过的事实。

### 12.2 Agent 输出约束

所有 AI 输出分为三类：

- `proposal`：待用户确认的候选计划；
- `derived_insight`：由结构化事实和规则推导出的观察；
- `action_suggestion`：用户可执行的下一步。

每条建议至少带：

- 依据事实 ID；
- 时间；
- 置信级别；
- 是否需要用户确认；
- 失败时的降级文案。

### 12.3 主动建议示例

已确认事实：

- 父母预计 12 月 28 日 13:00 到达老家；
- 年货预计 12 月 29 日 18:00 送达；
- 家庭聚餐安排在 12 月 28 日 18:00；
- 聚餐需要的食材尚未确认负责人；
- 当前已使用预算 ¥4,180 / ¥6,000。

Agent 建议：

> 目前聚餐时间早于年货送达时间，且食材任务还没有负责人。建议由一名成员在本地小程序采购当天食材，年货订单保留为后续补充；当前预算剩余 ¥1,820。该建议基于已确认的到达、送达、聚餐和预算事实，未读取任何第三方小程序内部页面。

## 13. Task Decomposition

### 13.1 拆解过程

1. 抽取实体：地点、时间、参与者、预算、目标对象和涉及服务；
2. 抽取约束：预算上限、必须条件、偏好、时限和不可接受条件；
3. 识别场景：从模板库选择最接近的任务类型，但不把场景当成产品边界；
4. 生成任务候选：按场景模板和 LLM 补充；
5. 标记任务类型：
   - `service_task`：适合绑定外部服务；
   - `coordination_task`：需要成员协作；
   - `decision_task`：需要选择方案；
   - `tracking_task`：预算、时间、状态等追踪项；
6. 建立依赖：例如到达时间影响聚餐，采购时间影响收货；
7. 为每个任务声明所需输入和预期输出；
8. 请求用户确认；
9. 用户编辑后锁定初始计划。

### 13.2 异地过年示例

```text
异地过年家庭团聚
├── 确认城市、日期与成员 [decision_task]
├── 跨城交通 [service_task]
├── 住宿 [service_task]
├── 年货采购 [service_task]
├── 家庭聚餐 [service_task]
├── 到达与收货安排 [coordination_task]
├── 预算 [tracking_task]
└── 家庭分工 [coordination_task]
```

MVP 只保证“异地过年”模板中的交通、住宿、年货、预算和家庭分工五项稳定生成；聚餐、到达安排等作为条件性任务。其他场景复用同一任务 schema，但在 V1 再加入模板和领域知识。

### 13.3 用户修改规则

- 用户删除的任务不得被下一次普通同步自动恢复；
- 用户新增的任务标记为 `user_added`；
- AI 重新拆解时生成新版本，不直接覆盖当前版本；
- 用户可选择“应用全部建议”或逐项接受；
- 已有事实和决策优先级高于 AI 候选；
- 任务状态只能由用户动作或明确事件推进，不能仅凭 AI 生成内容自动变成已完成。

## 14. Mini Program Discovery

### 14.1 Capability-first 流程

```text
Intent constraints
  -> Task requirements
  -> Capability filter
  -> Geographic/time/participant match
  -> Verified mini program candidates
  -> Explainable ranking
  -> User chooses tool
```

### 14.2 一个任务匹配一个还是多个小程序

使用以下决策：

- 一个小程序能完整覆盖任务，并有足够高的可用性：推荐一个；
- 任务需要不同能力，例如“交通查询 + 地图导航”：推荐主工具加辅助工具；
- 候选之间是替代方案：以方案组展示，不并列要求用户全部打开；
- 任务需要跨工具汇总：拆成多个子任务，分别绑定工具；
- 无核验候选：不推荐具体小程序，提供“手动记录任务”。

### 14.3 推荐排序

推荐分数由规则计算，不由 LLM 自由决定：

```text
score =
  capabilityMatch * 0.35
  + inputMatch * 0.20
  + geographyMatch * 0.15
  + timeFit * 0.15
  + verificationQuality * 0.15
```

若 `verificationQuality` 不达标，直接禁止展示为“可用工具”，只能展示为待核验候选。

## 15. Mini Program Capability Model

精选知识库的最小记录：

```json
{
  "id": "mp_verified_example",
  "name": "已核验服务小程序",
  "appId": "verified-or-null",
  "path": "verified-or-null",
  "shortLink": "verified-or-null",
  "category": "local_service",
  "capabilities": ["service_booking", "status_query"],
  "supportedTasks": ["transport", "lodging", "shopping", "meal"],
  "targetUsers": ["organizer", "family", "team"],
  "geographicScope": ["configured_scope"],
  "requiredInputs": ["date", "location", "people_count"],
  "expectedOutputs": ["service_name", "time_window", "price", "location"],
  "handoffMode": "navigate_and_manual_confirm",
  "verification": {
    "status": "verified",
    "lastCheckedAt": "2026-08-31",
    "checkedOnDevice": true
  },
  "source": "official_or_partner",
  "fallback": {
    "searchPhrase": "当前任务对应的服务小程序",
    "manualCaptureEnabled": true
  }
}
```

### 15.1 必填字段

- Identity：名称、AppID、路径或短链；
- Capability：能做什么、不能做什么；
- Task mapping：支持哪些任务；
- Input contract：需要哪些用户输入；
- Output contract：完成后可回传哪些字段；
- Scope：地域、时间、参与者类型和业务限制；
- Handoff：跳转、合作回传、用户手动确认；
- Verification：核验人、时间、设备、状态；
- Fallback：不存在、不可跳转或失败时的替代方案。

### 15.2 防幻觉原则

- LLM 只能从知识库的 `id` 中选择工具；
- 前端只渲染后端返回的已核验 `appId/path/shortLink`；
- 价格、库存、班次不放入永久知识库作为实时事实；
- 任何外部结果必须标记 `source`、`capturedAt` 和 `confirmedBy`；
- 找不到匹配时返回空候选，不补造名称；
- 知识库变更需要审计记录。

## 16. Workspace Context Model

Context 分三层：

### 16.1 Facts：可验证事实

事实是 AI 可引用的最小单元：

```text
factId
workspaceId
key
value
unit
sourceType: user_input | user_confirmed | partner_return | manual_capture
sourceRef
confidence
capturedAt
confirmedBy
isCurrent
```

示例：`familyMeal.startsAt = 2026-12-28T18:00+08:00`。

### 16.2 Events：发生过的行为

记录“谁在什么时候做了什么”，例如：

- 创建任务；
- 打开工具；
- 提交服务结果；
- 修改预算；
- 认领任务；
- 接受 AI 建议；
- 邀请成员。

### 16.3 Derived State：可重建状态

包括：

- 任务进度；
- 总预算、已用预算、剩余预算；
- 时间冲突；
- 未分配任务；
- 下一步建议；
- AI Summary。

Derived State 可以重新计算，不能作为唯一事实来源。

## 17. Multi-user Collaboration

### 17.1 权限

| 角色 | 查看 | 修改 Workspace | 修改任务 | 管理成员 | 删除 Workspace |
| --- | --- | --- | --- | --- | --- |
| Owner | 是 | 是 | 是 | 是 | 是 |
| Member | 是 | 受限 | 可修改被分配/开放任务 | 否 | 否 |

MVP 不设计复杂角色。Owner 可将任务设置为“所有成员可编辑”或指定 Owner；Member 默认只能修改任务、提交事实、评论和认领。

### 17.2 协作动作

- Owner 分享 Workspace；
- 受邀用户通过分享卡片进入；
- 用户登录后创建或加入成员记录；
- 看到当前任务、成员和最近活动；
- 认领任务或由 Owner 分配；
- 完成任务并提交结构化结果；
- 其他成员通过实时同步看到状态；
- AI Summary 更新并指出未完成任务。

### 17.3 AI 的团队价值

AI 不只显示“共享成功”，还应生成：

> 已完成：跨城交通、住宿。  
> 未完成：年货、家庭聚餐。  
> 当前没有负责人：家庭聚餐。  
> 预算已使用 ¥4,180，剩余约 ¥1,820。  
> 建议由还未认领任务的成员负责家庭聚餐。

## 18. Notification

### MVP

- Workspace 内红点和风险卡；
- 用户打开 Workspace 时显示变化摘要；
- 用户主动点击后请求订阅消息；
- 只发送用户已订阅且有明确业务事件的提醒。

### V1

- 任务到期提醒；
- 成员认领/完成通知；
- 预算变更通知；
- 冲突持续未处理提醒。

不允许将通知作为拉新或诱导分享手段。用户未授权订阅时，必须以 Workspace 内提醒代替。

## 19. Data Model

逻辑实体：

```text
User
  1 --- N WorkspaceMember N --- 1 Workspace
Workspace
  1 --- N Task
Task
  1 --- N TaskTool N --- 1 MiniProgram
Workspace
  1 --- N Fact
Workspace
  1 --- N Event
Workspace
  1 --- N Decision
Workspace
  1 --- N NotificationPreference
```

核心实体字段：

- `User`：`id`, `openidHash`, `nickname`, `avatarUrl`, `createdAt`；
- `Workspace`：`id`, `title`, `goal`, `scenario`, `ownerId`, `status`, `budget`, `startAt`, `endAt`, `version`；
- `WorkspaceMember`：`workspaceId`, `userId`, `role`, `status`, `joinedAt`；
- `Task`：`id`, `workspaceId`, `parentId`, `title`, `type`, `status`, `ownerId`, `dependsOn`, `sortOrder`, `source`；
- `MiniProgram`：知识库记录，不属于某个 Workspace；
- `TaskTool`：`taskId`, `miniProgramId`, `rank`, `matchReason`, `availability`；
- `Fact`：结构化事实和来源；
- `Event`：不可变活动事件；
- `Decision`：关键选择和影响；
- `AgentRun`：输入摘要、输出类型、模型、token、耗时、状态；
- `Invite`：`workspaceId`, `tokenHash`, `createdBy`, `expiresAt`, `maxUses`, `status`。

## 20. Permission Model

- 使用微信登录身份建立当前小程序内用户身份；
- 后端从可信登录上下文获取用户标识，不信任前端传来的 `userId`；
- 所有 Workspace 查询先校验成员关系；
- Owner 才能修改成员角色、删除 Workspace 和刷新邀请；
- Member 只能更新授权字段；
- AI 只能读取 Workspace Context 的最小必要字段；
- AppID、AppSecret、模型密钥只存在云端；
- 位置、录音、图片、剪贴板等敏感能力按需调用并配置隐私指引；
- 用户可以删除自己提交的可删除内容，并提供 Workspace 删除/退出路径；
- 日志不得记录完整的敏感个人信息、token 或第三方会话信息。

## 21. Error / Edge Cases

### Intent 与拆解

- 日期缺失：先生成相对计划，要求用户选择日期；
- 预算缺失：不虚构预算，显示“未设置预算”；
- 人数和预算冲突：标记为待确认；
- 用户拒绝 AI 计划：保留原始输入并提供空白 Workspace；
- AI 解析失败：给出结构化表单和示例，而不是空白报错。

### 小程序工具

- AppID/path 未核验：禁止直接跳转；
- 目标小程序不存在或被下架：显示不可用并提供搜索词/手动记录；
- 跳转被用户取消：不改变任务状态；
- 第三方没有回传能力：回到 Orbit 后要求用户确认结果；
- 用户在外部小程序中完成操作但没有回到 Orbit：任务保持 `in_progress`；
- 不把打开成功当成任务完成。

### Workspace 与协作

- 网络断开：本地显示最近快照，禁止伪造已同步状态；
- 并发修改：以版本号或服务端时间排序，冲突时提示用户；
- 邀请过期或被撤销：拒绝加入并说明原因；
- 非成员访问：只显示无权限页面，不泄露 Workspace 标题或成员；
- 成员退出：其任务回到“待分配”，历史事件保留；
- AI 建议与用户事实冲突：优先事实，建议标记为过期。

- Demo 中所有外部工具入口均已在目标真机验证；
- 任意 AI 文案都能指出依据，不能出现未核验事实。

## 25. Competition Demo Storyboard

### Scene 1：问题

演示者先展示传统链路：

```text
一句需求 -> AI 答案 -> 多个孤立的小程序链接
```

指出：链接之间没有共同目标、状态、预算和协作关系。

### Scene 2：创建 Workspace

用户点击语音或输入：

> 春节我和家人分散在不同城市，想一起回老家过年。请帮我安排交通、住宿、年货和家庭分工，预算 6000 元。

AI 展示结构化理解，用户确认成员、日期和预算是否包含交通与年货。

### Scene 3：任务被组织起来

出现：

```text
跨城交通 0%
住宿 0%
年货采购 0%
家庭聚餐 0%
预算 ¥0 / ¥6000
```

每个任务卡下出现“推荐工具”和推荐原因，而不是一个孤立列表。

### Scene 4：结果回到 Workspace

用户打开交通或购物工具并完成选择；回到 Orbit 后确认：

```text
出发城市 -> 老家
12 月 28 日 09:00 - 13:00
¥520 / 人
```

对应任务变为完成，预算和时间线自动更新。

### Scene 5：跨任务 Context 产生新价值

用户再提交年货或聚餐结果：

```text
聚餐 12 月 28 日 18:00
年货预计 12 月 29 日 18:00 送达
已使用预算 ¥4180 / ¥6000
```

AI 立即提示聚餐早于年货送达，且食材任务没有负责人，并给出本地采购和任务分工建议。

### Scene 6：微信生态协作

用户分享 Workspace 卡片；第二台设备加入，看到同一任务状态，认领“家庭聚餐”。第一台设备实时出现成员和任务变化。

### Scene 7：收束

演示者总结：

> 微信搜索帮你找到工具，AI 推荐帮你得到答案；Orbit 把工具、结果、进度和人组织成一个共同完成目标的空间。

## 26. 产品决策结论

1. **产品主场景是所有需要组合微信小程序的现实任务**，旅行、异地过年、搬家和聚会只是不同模板。
2. **异地过年是比赛代表性模板**，因为它能同时证明任务拆解、工具编排、Context 推理和微信协作，而不限制产品未来边界。
3. **“手动确认结果”不是临时妥协，而是 MVP 的可信边界**：在没有合法跨小程序数据读取能力时，用户主动提交比伪造自动化更可靠。
4. **精选知识库优先于搜索引擎**：比赛要展示推荐质量和可解释性，不要把时间投入到生态全量索引。
5. **规则引擎优先于 Agent 自主规划**：预算、时间和权限问题应可预测；LLM 负责理解和表达。
6. **协作是增强亮点，不得阻塞单人闭环**：即使没有第二台设备，单人也必须完成从 Intent 到 Context 的核心路径。
7. **真正的产品护城河是 Context 数据模型和任务工作流**，不是模型名称或推荐列表。
